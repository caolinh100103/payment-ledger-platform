# ADR 0016: The API contract: OpenAPI generated from the code, TypeScript types generated from it

**Status:** Accepted (Phase 6)

## Context

The web app calls three services. Written by hand, its request and response types would drift from the Java records
they describe: a field renamed in the backend, an enum value added, a property that can now be null. TypeScript
would still compile, and the bug would show up in front of a customer. The repository is a monorepo
([PLAN](../PLAN.md), decision 5) precisely so that an API change and its frontend change can land in one commit; the
build should insist on it.

## Decision

**Code first.** springdoc generates an OpenAPI 3.1 document from the controllers of each service, served at
`/v3/api-docs` with Swagger UI at `/swagger-ui.html`. Annotations only add what reflection cannot see: the `201`
status of creations, the `TransferResponse` returned as a raw JSON string by the idempotent endpoints, and which
fields may be `null`. Two customizers fill in the rest from the code itself:

- `operationId` = controller + method (`transfer_create`), stable across releases instead of numbered suffixes.
- Security requirements and an `**Access:**` note come from each operation's `@PreAuthorize` rule, the one that is
  enforced, so the document cannot claim a different rule.
- Every operation's `default` response is the `Problem` schema (RFC 9457 plus `code`), and every response property is
  `required` because Jackson always writes it; a property that can be absent says `nullable`.

**A committed copy, checked by the backend.** `frontend/openapi/{core,audit,notification}.json` are copies of the
three documents. `OpenApiContractTest` in each service compares the served document with the copy and fails on any
difference, with the command that regenerates it (`-Dopenapi.update=true`). Keys are sorted
(`springdoc.writer-with-order-by-keys`) and the server URL is relative, so the files are reproducible and their diffs
show only API changes.

**Types generated by the frontend.** `npm run generate:api` runs `openapi-typescript` on the copies and writes
`src/api/generated/*.ts`, also committed. The client is `openapi-fetch`, typed by those paths: the URL, path and
query parameters, the body and the response are all checked by the compiler.

**CI closes the loop.** The backend workflow runs on changes to `frontend/openapi/**` as well as to the services. The
frontend workflow regenerates the types and fails if they differ from the committed ones, then type-checks. An API
change therefore fails CI until the copy, the types and every use of them are updated together.

**Problems.** For the contract to say "every error has a `code`", it had to be true: Spring MVC's own errors
(malformed JSON, validation, unknown path, wrong method) now get one too (`INVALID_REQUEST`, `RESOURCE_NOT_FOUND`,
`METHOD_NOT_ALLOWED`…), and validation failures list the offending fields in `invalidParams`, the extension RFC 9457
uses as its example.

**Numbers.** Amounts are JSON integers in minor units (ADR 0002) and become JavaScript numbers. That is exact up to
2^53 − 1; RFC 7493 (I-JSON) asks for integers within that range. The largest amount the API accepts is 10^15
(`TransferLimits.MAX_AMOUNT`), below it. Amounts typed by a person are parsed as text into minor units, never via
floating point.

## Alternatives considered

- **Contract first** (write the YAML, generate Spring interfaces). Gives a reviewable contract before any code, and
  suits an API published to partners. Here the contract already existed as code, and generated server stubs would
  have to be bent around the idempotency handler, which returns stored bytes. The contract test gives the same
  guarantee (the document and the code agree) in the other direction.
- **Generating the spec in the build with the springdoc Maven plugin.** It starts the whole application, with its
  database and Kafka, during `mvn verify`. The contract test reuses the Spring context the integration tests already
  start with Testcontainers.
- **Not committing the generated TypeScript.** Keeps the repository smaller, but every checkout, editor and CI job
  would need a generation step first, and reviewers would not see how an API change reshapes the client.
- **A full generated SDK** (openapi-generator's TypeScript clients). Heavier, with classes and its own runtime;
  `openapi-fetch` is a thin typed wrapper over `fetch` with no generated runtime code.

## Consequences

- A backend change that alters the API cannot be merged without its frontend consequences: the contract test fails
  first, then the type check.
- Swagger UI documents every service for anyone exploring the API, with the access rule of each operation.
- The OpenAPI files are long and change with every API change; they are generated, not edited.
- The audit and notification services repeat the small OpenAPI configuration of the core. A shared library would
  remove that, at the price of coupling three independent deployables.
